## ТЗ: калькулятор электрики для квартир

### 1. Цель

SPA-приложение для предварительной оценки **стоимости материалов и сроков выполнения электромонтажа в квартире** на основании анкеты и выбранных опций, сами опции, их порядок и взаимосвязи - образуют чек-лист который позволяет не упустить моменты которые нужно заложить в начале выполнения работ.

Результат должен позволять электрику быстро сказать заказчику:

> «По предварительной оценке материалы выйдут примерно в 180–220 тыс. ₽. Основные статьи — кабель, щит и аппаратура, розетки/выключатели. Если отказаться от X и Y, можно сэкономить около 20 тыс.»

---

## 2. Стек

- **Svelte 5**
- SPA
- **TypeScript**
- **daisyUI / Tailwind CSS**
- `localStorage` для хранения проектов
- JSON Schema + **svelte-jsonschema-form** — использовать, если это упростит декларативное описание анкеты
- без backend на первом этапе

---

## 3. Сущность «Проект»

Проект содержит:

### Общие данные

- название/номер проекта;
- тип объекта: `квартира` (пока единственный);
- площадь;
- количество комнат;
- количество санузлов;
- кухня;
- балкон/лоджия;
- стадия объекта;
- комментарий.

# 4. Анкета

Анкета разбита на логические разделы.

### 4.1 Планировка

- комнаты;
- санузлы;
- кухня;
- балкон/лоджия;
- количество дверей;
- примерное количество точек.

Можно предусмотреть режим:

**«Пока нет точной планировки»**

с расчетом по типовым значениям.

- есть / нет;
- количество;
- отдельная линия;
- ориентировочная мощность.

Предварительный список:

- варочная панель;
- духовой шкаф;
- посудомоечная машина;
- стиральная машина;
- сушильная машина;
- холодильник;
- бойлер;
- полотенцесушитель;
- тёплый пол;
- кондиционер;
- измельчитель;
- прочее.

### 4.3 Кондиционеры

- необходимость закладки трасс;

### 4.4 Слаботочка

### 4.6 Санузлы / СУП

### 4.7 Датчики и автоматика

# 5. Щит

Отдельный раздел **«Пожелания к щиту»**, причём большая часть опций должна быть необязательной.

### Базовые параметры

- количество фаз;
- вводной автомат;
- тип системы заземления;
- номинал ввода;
- количество резервных модулей.

### Опциональные функции

- противопожарное УЗО;
- реле напряжения;
- реле контроля фаз;
- УЗИП;
- селективное УЗО;
- отдельные УЗО;
- дифавтоматы;
- неотключаемые линии;
- отдельная линия для холодильника;
- отдельная линия для интернета/оборудования;
- контактор;
- ручной/автоматический байпас;
- индикация напряжения;
- модульный ваттметр;
- ограничение мощности;
- резервные автоматы;
- дополнительный щит/слаботочный шкаф.

Важно: опции должны влиять **не только на стоимость, но и на состав материалов и количество модулей щита**.

# 6. Реестр материалов

Отдельный справочник материалов:

```text
Материал
├── категория
├── название
├── единица измерения
├── цена
├── артикул
├── поставщик
└── параметры
```

Категории:

- кабель;
- гофра;
- трубы;
- подрозетники;
- коробки;
- розетки;
- выключатели;
- автоматы;
- УЗО;
- дифавтоматы;
- реле;
- УЗИП;
- щиты;
- DIN-компоненты;
- клеммы;
- наконечники;
- крепёж;
- слаботочка;
- освещение;
- прочее.

Предусмотреть **коэффициент запаса** для разных типов материалов.

Например:

```text
Кабель:       +10%
Гофра:        +10%
Крепёж:       +15%
Розетки:       +5%
```

# 7. Расчёт материалов

На основании анкеты приложение формирует предварительную ведомость:

| Материал    | Количество |  Цена |    Сумма |
| ----------- | ---------: | ----: | -------: |
| ВВГнг 3×2.5 |      180 м | 120 ₽ | 21 600 ₽ |
| ВВГнг 3×1.5 |      120 м |  75 ₽ |  9 000 ₽ |
| Подрозетник |      45 шт |  35 ₽ |  1 575 ₽ |

Расчёт должен быть **правиловым**, а не зашитым непосредственно в компоненты UI.

Например:

```ts
if (project.rooms >= 2)
  addCable(...)

if (project.airConditioners > 0)
  addCircuit(...)
```

Это позволит впоследствии менять методику расчёта.

# 8. Категории стоимости

Обязательно показывать промежуточные итоги:

- Кабель
- Монтажные материалы
- Розетки/выключатели
- Щит и аппаратура
- Слаботочка
- Освещение
- Заземление/СУП
- Автоматика
- Прочее

И:

**Итого материалов**

с возможностью раскрыть каждую категорию до конкретных позиций.

### Экономия

Для дорогих/необязательных категорий показывать:

> Можно отказаться от опции «реле напряжения» → −X ₽

или:

> Премиальный вариант щита → +X ₽

То есть приложение должно помогать **обсуждать бюджет**, а не просто выдавать одну сумму.

# 9. Оценка сроков

Добавить ориентировочный расчёт трудозатрат:

```text
Подготовка трасс             X ч
Укладка кабеля               X ч
Подрозетники                 X ч
Сборка щита                  X ч
Установка розеток            X ч
Слаботочка                    X ч
Пусконаладка                  X ч
```

Настройки:

- количество электриков;
- коэффициент сложности;
- коэффициент неопределённости.

Результат:

> **Ориентировочный срок: 5–7 рабочих дней**

Важно обозначать это именно как **оценку**, особенно если планировка ещё не готова.

# 11. Хранение

`localStorage`.

Поддержать:

- несколько проектов;
- создание/копирование проекта;
- переименование;
- удаление;
- автоматическое сохранение;
- экспорт JSON;
- импорт JSON.

Экспорт особенно важен — позволит не потерять проекты при изменении структуры приложения.

---

# 12. Архитектура

Ключевой принцип:

**Анкета → нормализованная модель проекта → calculation engine → результат**

UI не должен содержать расчётную логику.

Для первой версии я бы **сознательно не делал полноценный проект электрики**.

MVP:

1. анкета квартиры;
2. потребители;
3. кондиционеры;
4. интернет/слаботочка;
5. СУП;
6. пожелания к щиту;
7. каталог материалов;
8. автоматический расчёт;
9. разбивка стоимости по категориям;
10. список возможностей для экономии;
11. ориентировочный срок;
12. сохранение проектов в `localStorage`;
13. импорт/экспорт JSON.

**Планировку с точным размещением розеток, трассировкой и визуальным планом** оставить на следующий этап. Это уже существенно другой класс приложения.

Я бы также сразу заложил версионирование схемы проекта (`schemaVersion`), поскольку калькулятор неизбежно будет менять структуру анкеты и формулы расчёта.
